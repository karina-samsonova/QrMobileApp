## 1. Зачем это нужно

Приложения для учёта расходов, кэшбэк-сервисы и «Проверка чеков» от ФНС умеют превращать бумажный чек в данные: сфотографировал — и покупка попала в историю с суммой, датой и списком товаров. Внутри у таких приложений две задачи компьютерного зрения, которые решаются по-разному.

- **QR-код.** По закону (54-ФЗ) он печатается на каждом кассовом чеке и содержит строку фиксированного формата: дату, сумму и фискальные признаки. Распознаётся почти всегда и **точно**. Но списка товаров в нём нет.
- **Текст чека (OCR).** Даёт позиции прямо с бумаги, без сервера. Но результат **вероятностный**: строки приходят с ошибками, в разном формате, иногда что-то теряется.

Ни один способ сам по себе не достаточен, а вместе они дополняют друг друга: QR задаёт эталонную сумму, OCR даёт позиции, а сверка «сумма позиций = итог = сумма из QR» показывает, можно ли доверять результату. Это типичная ситуация в мобильном CV (документы, банковские карты, паспорта): готовая модель распознаёт, а вся инженерия — в том, чтобы правильно разобрать и проверить её результат.

Обучать модели не нужно: используются **готовые библиотеки распознавания** (ML Kit, Vision, Tesseract и т.п.). Работа — в интеграции камеры и распознавания, разборе данных и проверке результата.

## 2. Что должно получиться

1. Пользователь наводит камеру на чек.
2. Приложение находит QR-код и показывает дату, сумму и тип операции.
3. Пользователь фотографирует чек, приложение распознаёт текст и показывает позиции (название, количество, цена, сумма) и итог.
4. Приложение сверяет данные и показывает статус: «всё сходится», «не сходится итог», «потеряны позиции», «нет QR, итог не подтверждён».
5. Для уровней П/Э: распознавание в реальном времени с подсветкой QR и строки итога на превью камеры, офлайн-история чеков без дублей, сравнение двух OCR-движков.

Плюс отчёт в PR: таблица сравнения QR и OCR на ваших собственных чеках.

## 5. Контракт модуля логики

Тесты проверяют поведение этих функций. Имена можно адаптировать к своему языку (например, `parse_qr` в Dart), структуру классов выбирайте сами.

**Деньги храните в копейках целым числом** (`Long`, `Int64`, `int`), не в `Double`. `0.1 + 0.2 != 0.3` в чеке недопустимо.

```kotlin
// Этап 1
fun parseQr(raw: String): QrResult
//   QrResult.Success(QrData) | QrResult.NotAReceipt | QrResult.MissingField(name) | QrResult.InvalidField(name)
data class QrData(
    val dateTime: LocalDateTime,   // из t
    val sumKopecks: Long,          // из s
    val fn: String,                // номер фискального накопителя
    val documentNumber: String,    // i
    val fiscalSign: String,        // fp
    val operationType: OperationType // n: 1 INCOME, 2 INCOME_RETURN, 3 EXPENSE, 4 EXPENSE_RETURN
)

// Этапы 2–3
fun parseReceiptText(lines: List<String>): ParsedText
data class ParsedText(
    val totalKopecks: Long?,       // этап 2
    val dateTime: LocalDateTime?,  // этап 2
    val items: List<Item>          // этап 3
)
data class Item(val name: String, val quantity: BigDecimal, val priceKopecks: Long, val amountKopecks: Long)

// Этап 3
fun reconcile(qr: QrData?, text: ParsedText): ReconcileStatus
//   OK | UNVERIFIED | TOTAL_MISMATCH | ITEMS_MISMATCH | NO_TOTAL

// Этап 5
class ReceiptHistory { fun save(qr: QrData, text: ParsedText?): Boolean; fun count(): Int }
```

`parseReceiptText` принимает **строки текста**, как их отдаёт OCR-библиотека (сверху вниз). Поэтому её можно тестировать без картинок и без устройства.

### Правила разбора QR

- Строка состоит из пар `ключ=значение`, разделённых `&`, порядок пар любой.
- Обязательные ключи: `t`, `s`, `fn`, `i`, `fp`, `n`. Если строка вообще не похожа на набор пар `ключ=значение` или в ней нет ни одного из этих ключей — `NotAReceipt`. Если часть ключей есть, а какого-то нет — `MissingField(<ключ>)`.
- `t` — дата и время в формате `ггггММддTччмм` или `ггггММддTччммсс`. Другой формат — `InvalidField("t")`.
- `s` — сумма в рублях: `1450.00`, `99.9`, `500`.
- `n` — тип операции от 1 до 4. Другое значение — `InvalidField("n")`.

### Правила разбора текста

- **Строка позиции** имеет вид `<количество> x <цена> =<сумма>`. Вместо `x` может быть `*` или кириллическая `х`, вокруг знаков могут быть пробелы, десятичный разделитель — точка или запятая, в числах может быть пробел-разделитель тысяч (`1 299.00`). Количество может быть дробным (весовой товар: `0.512`).
- **Название позиции** — до двух строк непосредственно над строкой позиции, если они не служебные и не являются строкой другой позиции. Строки склеиваются через пробел (ближняя к строке позиции идёт последней).
- **Служебные строки** не попадают в названия: `КАССОВЫЙ ЧЕК`, `ПРИХОД`, `ВОЗВРАТ ПРИХОДА`, строки, начинающиеся с `ООО`, `ИП`, `АО`, `ПАО`, а также строки итога и оплаты.
- **Итог** — сумма из строки, которая начинается с `ИТОГ`, `ИТОГО` или `К ОПЛАТЕ` (регистр любой, после слова может быть `:` или `=`). Строки `НАЛИЧНЫМИ`, `БЕЗНАЛИЧНЫМИ`, `ПОЛУЧЕНО`, `СДАЧА` итогом не считаются.
- **Дата** — первое вхождение `дд.мм.гг чч:мм` или `дд.мм.гггг чч:мм`.

### Правила сверки (`reconcile`), по порядку

1. Есть QR, есть итог из текста, и они не равны → `TOTAL_MISMATCH`.
2. Эталонный итог = сумма из QR, если QR есть, иначе итог из текста. Если эталона нет → `NO_TOTAL`.
3. Сумма `amount` всех позиций ≠ эталонному итогу → `ITEMS_MISMATCH`.
4. Есть QR → `OK`, нет QR → `UNVERIFIED`.

## 7. Этапы выполнения

### Этап 1. Камера и QR (≈2,5 ч) — обязательный

1. Создайте проект и модуль логики, настройте запуск его тестов одной командой.
2. Реализуйте `parseQr` и пройдите сценарии Q1–Q8.
3. В приложении: экран с превью камеры (CameraX `PreviewView` + `ImageAnalysis`), запрос разрешения на камеру, распознавание QR через ML Kit Barcode Scanning.
4. Найденный QR разбирается через `parseQr`, данные показываются на экране. Ошибки разбора показываются понятным текстом, а не падением приложения.

Документация: [CameraX: Getting started](https://developer.android.com/codelabs/camerax-getting-started), [ML Kit Barcode Scanning (Android)](https://developers.google.com/ml-kit/vision/barcode-scanning/android).

### Этап 2. OCR: итог и дата (≈2 ч) — обязательный

1. Кнопка «Сфотографировать чек» (`ImageCapture`) или выбор фото из галереи.
2. Распознавание текста на фото (ML Kit Text Recognition или Tesseract). Из результата соберите список строк сверху вниз.
3. Реализуйте в `parseReceiptText` поиск итога и даты, пройдите сценарии T1–T5.
4. Покажите на экране распознанный итог и дату, а под спойлером — сырой текст OCR (пригодится для отладки и в видео).

Документация: [ML Kit Text Recognition v2 (Android)](https://developers.google.com/ml-kit/vision/text-recognition/v2/android), [Tesseract4Android](https://github.com/adaptech-cz/Tesseract4Android).

### Этап 3. Позиции и сверка (≈2,5 ч) — обязательный

1. Реализуйте разбор позиций (I1–I5) и `reconcile` (R1–R6).
2. Экран результата: список позиций, итог, статус сверки с понятным пояснением (цвет и текст).
3. Если QR уже отсканирован на этапе 1, используйте его при сверке.

После этапа 3 у вас работающий сканер: можно идти в магазин и проверять на настоящих чеках.

### Этап 4. Реальное время и сравнение подходов (≈2 ч) — уровень П

1. Распознавание в реальном времени: на превью камеры рамкой подсвечиваются найденный QR и строка итога (координаты берутся из результата ML Kit / Tesseract и переводятся в координаты превью).
2. Таблица сравнения на **не менее чем 5 своих чеках** (разные магазины, мятый чек, плохой свет):

   | Чек | QR распознан | OCR: итог верный | OCR: позиций найдено / всего | Статус сверки | Время распознавания, мс |
   |---|---|---|---|---|---|

3. Короткий вывод (3–5 предложений): когда какой подход надёжнее и почему.

### Этап 5*. История и второй движок (≈2 ч) — уровень Э

1. Офлайн-история чеков в локальной БД (Room / SwiftData / sqflite и т.п.) с экраном списка. Повторное сканирование того же чека не создаёт дубль (сценарии D1–D2).
2. Подключите второй OCR-движок (например, ML Kit и Tesseract) с переключателем в настройках и добавьте в таблицу этапа 4 колонки для обоих. Сделайте вывод, какой движок лучше справляется с русскими чеками.

## 10. Частые проблемы

- **Чёрный экран вместо превью** — не выдано разрешение `CAMERA` или превью не привязано к lifecycle (`bindToLifecycle`).
- **В эмуляторе нет камеры** — Extended Controls → Camera → Back camera: Webcam0. Распечатанный или открытый на втором экране чек тоже подойдёт.
- **Названия товаров распознаются кракозябрами** — это ML Kit и кириллица (см. раздел 3). Возьмите Tesseract с `rus.traineddata` или зафиксируйте это в таблице сравнения.
- **QR не находится** — QR на чеке мелкий: поднесите камеру ближе, включите автофокус, задайте ML Kit формат `FORMAT_QR_CODE`, чтобы не искать все форматы.
- **Строки OCR идут не по порядку** — отсортируйте блоки/строки по вертикальной координате (`boundingBox.top`), а при равенстве по горизонтальной.
- **Тесты логики требуют Android** — значит, в модуль логики попали зависимости от Android SDK. Модуль должен быть чистым Kotlin/JVM.
